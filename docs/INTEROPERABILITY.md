# Independent qBittorrent interoperability

Executed on 2026-10-25 on Apple Silicon macOS. **PASS: five scenarios repeated
twice, ten successful cases, 6,947,698 bytes compared exactly.** All selected
files also have recorded SHA-256 hashes. No public swarm was used.

Peer: qBittorrent `v5.3.0alpha1`, libtorrent `2.1.0.0`, Qt `6.10.3`,
Boost `1.91.0`, OpenSSL `3.6.3`. This is evidence for the installed development
build, not certification against every qBittorrent release.

The magnet case passes only the info hash and local tracker URL to the lab.
It resolves real metadata through the application core, adds the returned
metainfo, and verifies the selected file bytes. The skipped middle file is
piece-aligned and its final downloaded byte count must remain zero. This does
not imply that an unselected file is never created or preallocated on disk.

## Readiness finding

The original reverse transfer failed before a peer handshake completed.
On the follow-up, an independent Python handshake probe was also closed while
qBittorrent already reported `progress=1` and `stalledUP`. Without changing the
production engine, a later connection transferred the complete 1 MiB fixture
with the expected hash. No peer-block reason was reported.

The test harness now requires a complete 68-byte BitTorrent handshake with the
expected protocol header and info hash before starting a SeedHop download.
It retries only within a bounded 30-second startup deadline, recording all
attempts. The six download cases in the repeated suite needed 4–5 probes each;
early probes closed or reset, followed by valid handshakes and successful transfers.

This demonstrates that API completion alone was an insufficient readiness
condition in the test harness. The internal cause of every earlier reset is
not established. A failed protocol-readiness deadline remains a failed case;
the harness does not silently switch direction or bypass integrity checks.

## Isolation and reproducibility

```sh
python3 scripts/interop.py                         # five scenarios
python3 scripts/interop.py --repeat 2              # the recorded repeated suite
python3 scripts/interop.py --direction download --case magnet
python3 scripts/interop.py --qbit /path/to/qbittorrent
```

- Metainfo and deterministic data are generated by an independent Python encoder;
  the peer validates v1 piece hashes. The harness compares actual destination
  bytes with the generated source and records SHA-256 for every selected file.
- Each case has its own profile, session directory, payload, and destination.
  Existing qBittorrent profiles, SeedHop libraries, and their processes are not used.
- Peer and tracker traffic uses IPv4 loopback; qBittorrent binds to `lo0`.
  DHT, PEX, local discovery, UPnP, encryption, and queueing are disabled for the
  fixture peer. Ancillary qBittorrent update checks are outside this transfer
  test's network claim; no system network settings are changed.
- The test WebUI binds to loopback in the temporary profile. It is not the
  SeedHop remote-control feature and does not change SeedHop's product configuration.
- Deadlines cover startup, seed verification, handshake readiness, metadata,
  and transfer completion. Cleanup terminates only processes created by the case.
- `.build/interop-result.json` is the current machine report. Each retained
  `.build/interop-*/` directory includes `result.json`, engine and qBittorrent
  logs, tracker announcements, peer-block logs, build information, and, for
  downloads, handshake-readiness attempts and the final engine snapshot.

The portable recorded summary is [results/interop-2026-10-25.json](results/interop-2026-10-25.json).
Its artifact paths are relative to the repository root; raw logs remain in
the referenced local `.build` directories.

## Scope limits

These checks cover small v1 payloads, plain TCP, an HTTP tracker, real metadata
exchange, and a piece-aligned skipped file. They do not certify MSE encryption,
uTP, DHT discovery, IPv6, private trackers, v2/hybrid, long-running public swarms,
cross-piece file-selection edges, or behavior under disk/network failures.
Signed background/login lifecycle and manual UI/accessibility acceptance remain
separate gates in `VALIDATION.md`.
